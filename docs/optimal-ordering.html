The ordering problem

A backlog can be tidy, prioritized, and topologically valid while still being the wrong order for a product. Architecture inventories answer “what exists?” Dependencies answer “what can happen?” Neither answers “what should we learn and deliver next?”

A plan can be topologically valid and still be product-order wrong.

Importance is conditional. A large feature may matter eventually, but a small experiment may matter more now if it can settle the assumption that makes the rest of the plan safe. Order changes the evidence available, the cost of being wrong, the options kept open, and the amount of rework that follows.

Component inventory

“Build the data model, then the API, then the interface.” This describes parts. It can produce impressive completion with no coherent user journey.

Value order

“Let one real user attempt the job, observe the result, and decide.” This describes evidence. Parts are pulled through only when the journey needs them.

Optimal here is practical, not mathematical: a reasoned order that is recomputed as reality speaks. The objective is trustworthy evidence early, not a claim that uncertainty can be eliminated.

MVP means a coherent test, not a cheap pile

The minimum viable product is the smallest coherent end-to-end path where a real user attempts a meaningful job, the system produces an observable result, and the team can make a Stop, Pivot, or Continue decision.

Real job

Someone with a stake tries to accomplish something that matters outside the ticket system.

Observable result

The attempt creates evidence: a response, decision, completed action, failure, delay, or refusal.

Decision rights

The team has a threshold and a next move. “Interesting” without a decision is not an MVP.

An MVP is not permission for poor quality, and it is not the cheapest collection of features. A narrow path can still require reliability, privacy, accessibility, safety, or operational work when those are part of the promise. “Minimum” describes the scope of the learning journey. “Viable” describes whether the journey can be trusted enough to judge.

The vehicle ladder

Use a vehicle metaphor to force a useful question: does every rung transport the user? Start with a complete but narrow vehicle, then make the same journey more controlled, usable, lovable, and broad. Do not build wheels, axles, and seats as separate milestones while the vehicle remains unable to move.

The ladder is not a mandatory release plan. It is a guardrail against component milestones and a reminder that a later rung must preserve the user’s ability to travel.

Three evidence gates

“Working” is too vague to order work. Name which kind of evidence the next slice must earn.

Earliest Testable

A real or representative user can attempt the core job through a narrow path. The system exposes enough of its behavior to falsify the riskiest assumption.

Gate

Attempt recorded; result observable; falsifier and decision threshold are explicit.

Earliest Usable

The path can be repeated by its intended user without special rescue from the builder. It handles the normal path and communicates the important failure states.

Gate

A user completes the job with acceptable effort, clarity, and reliability for the declared context.

Earliest Lovable

The experience earns preference: it is clear, trustworthy, considerate, and meaningfully better than the workaround for its chosen job.

Gate

Observed preference or repeat behavior crosses a stated threshold; delight is evidence, not a mood.

These gates are nested, not cosmetic labels. A “lovable” surface that cannot be trusted is not lovable. A broad feature set that has never been testable is inventory, not a product.

Why order changes the outcome

Execution order changes what the team knows before it commits further. It changes cost of delay, risk exposure, rework, option preservation, and which downstream work can safely unlock.

Information value

Prioritize work that can settle a consequential unknown. A cheap falsifier may outrank a large build.

Cost of delay

Some learning loses value if postponed: a safety concern, a contractual boundary, or a decision that gates a launch.

Rework and reversibility

Test high-impact, hard-to-undo assumptions before polishing choices that depend on them.

Downstream unlock

Prefer a slice that opens several safe next moves, while discounting “unlock” claims that are only habits or preferences.

Importance is not a permanent property of an issue. It is a relationship between the issue, the current outcome, and the uncertainty that still matters.

Vertical slice or component milestone?

A vertical slice crosses the minimum layers needed to prove a user outcome. A component milestone completes one layer. Both are real work; they do not produce the same evidence.

ShapeExampleEvidence earnedTypical danger
Vertical sliceOne operator sends one request, receives one clear result, and can act on it.Does the end-to-end promise work for a real job?Scope can be mistaken for production breadth.
Component milestoneFinish the generalized service, schema, and client library before any journey is runnable.Is a part complete according to its own interface?Completion masquerades as product progress.
Required infrastructureIdentity, audit, rollback, or a rate limit needed to run the narrow journey safely.Can the slice be trusted in its declared context?It becomes a “basecamp” with no evidence gate.

Infrastructure is product work when it is a hard dependency or a material risk reducer for the promised slice. It is not itself user value merely because it is difficult. Proof machinery must not masquerade as a product milestone: tests, dashboards, and reconciliation make a claim trustworthy; they do not automatically make the claim valuable.

Two graphs, two questions

Do not confuse the dependency graph with the delivery order. One describes possibility. The other is a decision about value now.

Dependency DAG

Directed edges say what must precede what. It should be acyclic after splitting cycles into an interface, a stub, or an experiment.

Question: what is possible?

Delivery sequence

A time-ordered choice among ready work. It considers evidence value, risk, delay, coordination, and the current user promise.

Question: what is valuable now?

Type every edge

Edge typeMeaningRule
HardThe later item cannot safely or meaningfully execute without the earlier one.Only a verified hard edge blocks. Name the property that makes it hard.
EvidenceThe earlier item supplies an observation needed to choose or judge the later one.It changes confidence, not necessarily feasibility.
ResourcePeople, environments, permissions, or scarce equipment collide.Schedule the collision; do not invent a conceptual dependency.
PreferenceA convention, aesthetic, or default habit says “do this first.”Challenge it. Preference never blocks by itself.

Challenge and rewrite accidental edges. If two items appear cyclic, split the interface from the implementation, create a thin stub, or run an experiment that resolves the mutual assumption. A cycle is usually a signal that the work is too coarsely sliced.

One product spine, a few useful lanes

Keep a sequential spine for the user promise. Add parallel lanes only where parallel work is independently useful and has a clear join.

Fake parallelism is serial work hidden in two columns. It increases coordination and makes the first coherent evidence later. Keep the number of lanes small enough that a person can name the join condition without a meeting.

A decision objective, without fake precision

For each ready candidate, ask how much trustworthy value and learning it can buy before more time, coordination, and irreversible commitment. Use ordinal scales such as low, medium, and high. The formula is a thinking aid, not a measurement system.

Choose the next slice that maximizes (validated user value + learning + important risk retired + downstream unlock) ÷ (time to evidence + coordination cost + irreversibility cost)subject to hard safety, authority, and dependency gates · use explicit judgments, not invented decimals

“Value” must be tied to the current outcome. “Risk retired” must name a consequential risk. “Unlock” must identify a real next decision. Penalize slices whose evidence arrives late, whose coordination surface is broad, or whose commitment is hard to undo. A small experiment can win because it changes the order of everything after it.

The practical ordering algorithm

Run this as a loop, not as a one-time planning ceremony. The current milestone is a bet with a gate; new evidence is allowed to rewrite the bet.

  1. Observe current reality. Inspect the running behavior, constraints, recent changes, users, incidents, and available evidence. Record what is known, unknown, and merely assumed.
  2. Define the user, job, outcome, and non-goals. State who attempts what, what observable result matters, and what this order deliberately does not solve.
  3. Rewrite the backlog as outcomes or experiments. Replace “build service X” with a claim about user behavior, a risk, or a decision the work will settle.
  4. Find the core loop. Trace the smallest path from trigger to user action to system result to next decision. Everything else is an extension until proven otherwise.
  5. Type dependency edges. Label hard, evidence, resource, and preference edges. Verify blockers. Challenge accidental edges; split cycles with seams, stubs, or experiments.
  6. Identify the Earliest Testable slice. Pick the smallest coherent journey that can expose the riskiest consequential assumption and produce observable evidence.
  7. Filter the candidate set. Remove work that is not ready, unsafe, unauthorized, blocked by a verified hard edge, or incoherent with the current user promise.
  8. Rank the ready set. Use the objective above lexicographically: hard gates first; then earliest evidence, decision value, risk retired, unlock, cost of delay, and reversibility. Break ties toward the narrower slice.
  9. Build the spine and lanes. Put the chosen user journey in sequence. Add only independently useful parallel work with bounded WIP, contracts, and an explicit join gate.
  10. Define the milestone contract. Write the user promise, complete demo journey, exact issue order, evidence threshold, falsifier, deferrals, and Stop/Pivot/Continue rule before execution.
  11. Execute the current milestone only. Keep scope bounded. Do not silently spend the next decision’s budget while the current evidence is still unresolved.
  12. Reconcile evidence. Compare the observed result with the acceptance evidence, metric baseline, threshold, and falsifier. Resolve against what landed and what the user actually experienced.
  13. Stop, Pivot, or Continue. Stop when the premise is falsified or value is absent; Pivot when evidence changes the slice or strategy; Continue when the gate is met and the next assumption is worth testing.
  14. Recompute, reslice, or end. Re-type dependencies, reorder the remaining work, split oversized slices, or close the effort when the outcome is met. The order is a living artifact.

Compact pseudocode

while outcome_not_met:
  reality = observe_system_and_user()
  goal, non_goals = define_job_and_outcome(reality)
  candidates = rewrite_as_outcomes_or_experiments(backlog)
  graph = type_and_verify_edges(candidates)
  slice = smallest_coherent_testable_path(goal, graph)
  ready = filter(candidates, ready_and_safe_and_coherent)
  next = argmax(ready, by=ordinal_value_of_evidence_per_cost)
  spine, lanes = arrange(next, parallel_only_if_join_is_explicit)
  contract = write_gate(spine, lanes, falsifier, threshold)
  execute(contract)
  result = reconcile_against_landed_user_evidence(contract)
  decision = stop_pivot_continue(result)
  backlog = recompute_and_reslice(backlog, graph, decision)
  if decision == STOP: break

Make order inspectable with contracts

An issue is a memory of a decision, not a command to a component. A milestone is a promise about a journey, not a count of closed tickets.

Issue contract template

OutcomeWhat user or system result should change?
BehaviorWhat will a person or system actually do?
HypothesisWhat must be true for this to be worth doing?
Slice / experimentWhat is the narrowest evidence-producing form?
Acceptance evidenceWhat observation type would count?
Metric / baseline / thresholdWhat is measured, from where, and how much is enough?
Typed dependenciesHard, evidence, resource, or preference edges.
Time to evidenceHow soon can the claim be judged?
Risks / irreversibilityWhat could hurt, constrain, or be costly to undo?
FalsifierWhat observation would retract this issue or approach?
Stop / Pivot / ContinueWhat result triggers each decision?
UnlocksWhich next decision becomes safer or possible?

Milestone contract

User promise: one sentence a user could recognize.

Complete demo journey: the trigger, action, result, and decision from start to finish.

Exact order: sequential issues, parallel lanes, and explicit join or gate.

Product value: why this journey matters now.

Hypothesis and metric: the belief, observed measure, baseline, and threshold.

Falsifier: the result that would make the approach wrong.

Explicit deferrals: what is intentionally not in this milestone.

Stop / Pivot / Continue: the decision table after observation.

A milestone closes against user-journey evidence, not because tickets closed.

Worked example: incident response

Imagine a team helping an on-call operator respond to a service incident. The domain is generic; the ordering lesson is the point.

Component-first orderValue-first ladder
General event schema → alert platform → routing rules → dashboard → acknowledgment UI → escalation.Testable: one real signal → one alert → one operator acknowledgment, with an observable audit record.
It may be technically coherent, but the team learns late whether an operator trusts the alert, sees it, or knows what to do.Controlled: add reliable delivery, deduplication, and a clear failure state for the chosen channel.
More components create more surfaces to maintain before the core response loop is judged.Usable: add the normal incident context, repeatable handoff, and the minimum recovery path.
Broad coverage is mistaken for readiness.Lovable / broad: improve signal quality, preference, escalation, and resilience only after evidence justifies expansion.

The first order optimizes for component completion. The second optimizes for the earliest trustworthy answer to: “When a real signal matters, can an operator notice it, acknowledge it, and make the next decision?” If that answer is no, the backlog should change before the dashboard gets prettier.

Failure patterns to catch early

Global backlog ranking

One permanent ranking ignores changing uncertainty and the current outcome.

Infrastructure basecamp first

A long platform phase delays evidence and makes sunk cost feel like strategy.

Fake parallelism

Two lanes share hidden decisions, so coordination grows while the journey remains untestable.

Proof-as-product

Tests, dashboards, and merged code are treated as user value without a user result.

Milestone by merged tickets

Ticket closure says little about whether the complete journey works.

Architecture rewrite before learning

High-irreversibility decisions are made before the riskiest assumptions are observed.

Predetermined ladder

Every rung is scheduled in advance, leaving no room for a falsifier to change direction.

Vague metrics and long preflight

“Improve experience” cannot trigger a decision, and overlong setup hides the absence of a slice.

The algorithm’s output

At the end of an ordering pass, you should have durable artifacts that let another person reconstruct why this sequence exists:

Product spine

The sequential user journey and its current promise.

Issue waves

Bounded groups ordered by evidence gates, not component labels.

Parallel lanes

Independent work with contracts, WIP limits, and joins.

Dependency rewrite ledger

Verified blockers, challenged edges, and cycle splits.

Milestone gate contracts

Promises, metrics, falsifiers, deferrals, and decisions.

Parking lot and evidence trail

Deferred ideas plus the observations that changed the order.

The ordering discipline inside Aegis Method

Optimal ordering is not a sixth move bolted onto the method. It is the discipline inside the five moves:

Aegis principleOrdering implication
Evidence before architectureObserve the current journey and its constraints before committing to a large dependency order.
Strategy before planChoose the current outcome and uncertainty before ranking issues.
Issues as memoryStore the order, contracts, assumptions, and revisions where the next person can inspect them.
Falsification before confidenceEvery slice names what would change the order or kill the approach.
Closure against realityClose milestones against observed journey evidence, not intention or bookkeeping.

What this does not claim

  • It does not produce a provably optimal schedule or remove judgment.
  • It does not say component work is bad, only that its product value must be named and evidenced.
  • It does not make safety, authority, quality, or compliance optional in a narrow MVP.
  • It does not require sequential work everywhere; it requires parallel work to be real, bounded, and joinable.
  • It does not replace domain expertise, user contact, or honest thresholds.

Field checklist

  • Have we named the user, job, outcome, and non-goals?
  • Can one narrow journey produce observable evidence?
  • Is the current slice testable, usable, or lovable by a stated gate?
  • Are issues written as outcomes or experiments?
  • Which assumption is most consequential and still uncertain?
  • Have all edges been typed, and are blockers truly hard?
  • Could a smaller slice settle the decision sooner?
  • Does each parallel lane have a contract, WIP bound, and join?
  • What are the metric, baseline, threshold, and falsifier?
  • What is explicitly deferred, and why?
  • What result triggers Stop, Pivot, or Continue?
  • Will closure be reconciled against the complete user journey?

If the next issue cannot make the next decision clearer, it is probably not the next issue.

This is a generic Aegis Method Lite field guide. Use it to make order inspectable, evidence early, and revision ordinary. The strongest plan is the one reality can change.
